## 5. Minimum architectural changes (STEP 5)

Recorded as ADR-0010 (product layering) and ADR-0011 (action policy levels). Summary:

1. **Four layers mapped to the monorepo** [HYPOTHESIS — structure; the layering itself is CONFIRMED by the Direction]:
   - **Core** = `packages/core` (exists).
   - **Business Platform** = `apps/api` (step 12: HTTP delivery, composition root, CLI) and later `apps/web` (Next.js dashboard + agent surface). Platform-level application services (workspace configuration, attention items, agent conversation) live in `packages/core/src/platform/` once they exist — same rules as modules.
   - **AI Systems** = `packages/systems/<system>/` workspace packages depending on `@dolmir/core` only (tools, workflows, schemas, prompts, evals of one capability). Created when the first system is built, not before (no empty folders).
   - **Company-specific AI** = configuration in the database (rules, terminology, policies, connectors, workflows) and, only when code is genuinely needed, `packages/tenants/<slug>/` depending on core and systems. Dependency-cruiser will enforce: systems → core public API only; tenants → core + systems; apps → all of the above; nothing imports apps.
2. **Action policy levels** (Direction §13): every tool declares its `effect` — `read`, `analyze`, `draft`, `act`. A versioned, code-defined default policy maps effects to `READ_ONLY | SUGGEST | DRAFT | REQUIRE_APPROVAL | AUTO_EXECUTE`; the tool executor enforces it; per-tenant overrides are a configuration table added with the first workflow. `act` tools require a persisted approval reference; none exist yet, so in Phase 0 an `act` tool cannot run. AI actors can never hold `decisions:approve`. **Implemented in step 11.**
3. **Agent architecture** [HYPOTHESIS]: Core provides the provider port, the tool framework and the executor (the permission boundary). The agent loop (conversation state, planning, tool calls, explanation with evidence) is a Platform component built with the first workflow, using the vendor SDK's tool runner inside the Anthropic adapter where useful. The agent never receives credentials, a database handle or an unbounded tool.
4. **Connector abstraction** [HYPOTHESIS]: `ConnectorPort` family (inbound sources: mailbox, drive, ERP export; outbound actions: send message, create record) with per-tenant encrypted credentials (`tenant_connections`). n8n becomes one connector runtime among others. Built with the first connector the first workflow needs (mailbox).
5. **Jobs and workflow execution** [HYPOTHESIS]: pg-boss (Direction §16) behind a `JobQueuePort` when the first asynchronous pipeline (document ingestion) needs it. Same database, same transaction semantics, no extra service.
6. **Company memory** [HYPOTHESIS]: structured, versioned tables (`company_profile`, `company_rules`, `terminology`, entity tables) plus retrieval indexes (pgvector behind a `RetrievalIndexPort`) used as evidence sources, never as the system of record. Built with the first workflow.
7. **Data access library** (Direction §16 names Drizzle) [HYPOTHESIS — owner may decide otherwise]: the repositories built so far use SQL migrations as the schema source of truth, `pg`, and Zod row schemas; RLS with transaction-local settings works with this stack today and is tested. Recommendation: **defer** Drizzle; adopt it for query building in the first workflow's modules if the wider schemas make it pay, keeping SQL migrations authoritative. Rewriting working repositories now would cost time and add no product capability.
8. **Dashboard** (Next.js, React, Tailwind) [HYPOTHESIS]: `apps/web` in this repository, built in Phase 2 against the API; the public website stays in `prova_1` as directed. Decision needed only when Phase 2 starts.

Nothing in Phase 0 steps 11–13 is blocked by these changes. Step 11 absorbs item 2; the rest are roadmap items.

| E. Customer communication follow-up (unanswered requests, SLA)                           | high   | daily      | medium–high                           | high                                                                           | high                                           | high                                                           | Part of A: "which requests are still unanswered?" is the first question the agent must answer.                                       |

**Chosen: A (with E folded in) — "Commercial Inbox Intelligence".** The end-to-end chain required by Direction §20:

```
DATA        shared commercial mailbox (connector) + customer list + company rules
UNDERSTAND  classify message → extract request fields with verbatim evidence spans → resolve customer
REASON      completeness, urgency, conflicts (body vs attachment), unanswered requests, priority
EVIDENCE    every claim cites message/attachment spans or records; gaps → NON DETERMINATO
RECOMMEND   "reply asking for X", "acknowledge and route to estimator", "no action" — with why
APPROVAL    a human approves the draft (policy level REQUIRE_APPROVAL for sending)
ACTION      send the approved reply through the mailbox connector (idempotent, audited)
RESULT      outcome recorded (answered, time to answer, follow-up needed) → ledger → memory
```

Out of scope for the first system: autonomous pricing, drawing interpretation, ERP write-back. Material intelligence remains candidate module #3 with its evidence vocabulary preserved (documented, ordered, receipt_claimed, receipt_confirmed, available, reserved, consumed_reported, consumed_confirmed, scrapped, returned, adjusted; invoice ≠ physical receipt).
