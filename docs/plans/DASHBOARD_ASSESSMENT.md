## 2. Current backend capabilities relevant to the Dashboard

Routes live in `apps/api/src/http/routes/*.ts`. Every tenant route requires a bearer JWT, membership resolved inside the tenant's row-level-security scope, and a named permission. Errors are RFC 9457 `application/problem+json` with `code`, `detail`, `requestId` and, for client errors, `errors`. Every response carries `x-request-id`, `x-correlation-id`, `cache-control: no-store`. [CONFIRMED]

| Route                                                                                                                  | Permission                                | What the dashboard gets                                                                                                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/me`                                                                                                           | token                                     | principal (subject, email, displayName, **expiresAt**) and the user's organisations with `roleKey` — the organisation switcher                                                                                                           |
| `GET /v1/orgs/:orgId`                                                                                                  | `organization:read`                       | organisation, membership, **`permissions[]`** for this membership, `roleMatrixVersion` — the one source for showing or hiding UI                                                                                                         |
| `GET …/cases?status&kind&systemKey&limit≤200`                                                                          | `organization:read`                       | the attention list, ordered **high priority first, then newest**; no paging cursor exposed (the repository supports `before`), no counts                                                                                                 |
| `GET …/cases/:caseId`                                                                                                  | `organization:read`                       | `{ case, findings, recommendations, approvals, actions }` — the whole detail in one call                                                                                                                                                 |
| `POST …/recommendations/:id/approve` · `/reject`                                                                       | `decisions:approve`                       | body `{ note?, execute = true }`; returns `{ recommendation, action }` where **`action` is `null` until a worker has run**; refuses `RECOMMENDATION_ALREADY_DECIDED`, and `RECOMMENDATION_NOT_EXECUTABLE` for READ_ONLY / SUGGEST levels |
| `POST …/cases/:caseId/resolve`                                                                                         | `decisions:approve`                       | `{ resolution: resolved_manually \| dismissed, note? }`; refuses `CASE_ALREADY_CLOSED`, `ACTIONS_PENDING`                                                                                                                                |

| `PATCH …/workspace/profile` · `PUT …/workspace/rules/:key` · `POST …/workspace/terminology` · `PUT …/workspace/policy` | `workspace:manage`                        | the settings writes; a rule write returns the new version with its rationale                                                                                                                                                             |
| `POST …/entities/import`                                                                                               | `entities:manage`                         | CSV import of customers, suppliers, contacts, products — **the only way to add or alias an entity**                                                                                                                                      |
| `GET` / `POST …/connections` · `POST …/connections/ingestion-keys` · `POST …/connections/:id/status` · `/poll`         | `connections:read` / `connections:manage` | connections without credentials (status, lastError, lastSyncAt, non-secret settings); an ingestion secret **shown once**; poll a mailbox now                                                                                             |

Two facts shape the interface more than any other: **the model never sets a business value** (every quantity, date and name in a finding is a verified span or a record field; readings that did not verify are listed as discarded), and **approval and sending are separate moments** (an approval returns before anything is sent; the reply leaves from a worker and the case reports it afterwards). There are **no confidence percentages** in Core: certainty is expressed by the epistemic status of each finding and by NON_DETERMINATO, not by a number. [CONFIRMED]

What does **not** exist and a dashboard will meet: no read endpoint for entities (customers, suppliers, products, aliases); no members endpoint (approvers are user ids); no paging or counts on cases; no search; no policy overrides, rule rationale, version or history in the workspace read; no endpoint listing the registered AI Systems; no outcomes or metrics (the ledger has no endpoint; the case-metrics projection of `PHASE2_FIRST_AI_SYSTEM.md` is not built); no bearer-authenticated upload; no case assignment or ownership; no comments on a case beyond a decision note; no way to edit a proposed draft; no agent conversation (M9); no notifications feed; no rate limiting, no CORS, no server-sent events. [CONFIRMED]

## 3. Existing DOLMIR website and design language

The site is a documented, token-first system; its principles are written down and its decisions are checkable. [CONFIRMED unless marked]

- **Identity, in the site's own words:** "OFFICINA DIGITALE. The reference is not a software company. It is a well-lit machine shop at night: near-black ground, machined surfaces catching one cold light, hairline rules like a drawing sheet, and a single instrument colour used only where a measurement is being reported." (`globals.css` header). Design research (`docs/DESIGN-RESEARCH.md`) measured Linear, Attio, Clay, ElevenLabs, Anthropic and Vercel and concluded: product as the illustration, one reading size and one display weight, restraint in colour, motion that explains, hairline discipline.
- **Rules that hold everywhere:** no component hard-codes a colour, size, radius, duration or easing; **amber means uncertainty and is never decoration** ("when it appears on screen, the system is telling you it is not sure — that is the whole brand"); corners are square ("industrial work is square; rounded reads as SaaS"); "colour as meaning: ink ladder for prose; accent (cyan) = information and the system at work; good (green) = VERIFICATO; amber = CONFLITTO, NON DETERMINATO, DECISIONE RICHIESTA and APPROVAZIONE UMANA — everything that means the system stopped for a person. Nothing else is coloured."
- **What the site is not allowed to borrow:** pill buttons and 12 px radii; light grounds as the default; customer walls and figures.
- **Voice** (`content/site.ts` header): never "rivoluzionare", "potenza dell'AI", "soluzioni innovative"; name the work, not the technology; never a number that was not measured or sourced; Italian first, "any English where Italian exists" is forbidden (`DOLMIR_FINAL_POSITIONING.md` §14). Words in use: rilievo, carico, preventivista, gestionale, commessa, conto terzi, pratica, registro, approvare.
- **The product is already drawn.** `components/product/primitives.tsx` — `Chip`, `Frame`, `Mail`, `Field` (label, value, source, state), `Check` (what, against, ok / conflict / pending), `Decision` (question, detail, APPROVA / REVISIONA, "decisione registrata"), `Actions` (✓ / ○ list); `components/demo/parts.tsx` — `Pane` (a frame whose body scrolls inside itself), `Tag`, `Verdict`, `Confidence`. The hero (`HeroStage.tsx`) is **three surfaces of the real interface side by side — "Posta commerciale · DOLMIR · Esito": what arrives, what DOLMIR makes of it, what comes out** — with one request walking across them. The case chapter says it plainly: _"Nell'interfaccia vera i pulsanti sono attivi."_ The dashboard is that real interface.
- **The console** (`components/live/Parla.tsx`, `docs/PARLA-CON-DOLMIR.md`): "the product itself, not a chat box on a marketing page". A frame with an instrument head (the Core, a status chip), a transcript, a side panel "Cosa sta facendo" with the stages ANALISI → DATI → VERIFICA → DECISIONE → RISPOSTA and "DATI CONSULTATI", the human gate (DECISIONE UMANA · APPROVA / MODIFICA / RIFIUTA · DECISIONE REGISTRATA) and NON DETERMINATO ("COSA MANCHEREBBE"). It is the precedent for any agent surface in the dashboard.
- **Positioning the dashboard must serve** (`DOLMIR_FINAL_POSITIONING.md`): "Il collo di bottiglia non è in officina" — office throughput in a manufacturing SME; "Più richieste evase, con le persone che avete già"; the measurement is installed so the client verifies instead of trusting; "a human approves every output". The solutions page names the analytics stance: **"Le anomalie, non le tabelle"** — the system signals what does not add up instead of producing a report to read.
- **What the dashboard does not copy from the site:** the marketing devices — `SystemBackdrop` (grid, light pool, vignette), `.sheet` / `.plate` / `.grain` / `.pool`, `Reveal` scroll entrances, `Chapter` headers, the display-xl scale, the film, the 3D. They belong to presentation; the product layer (frames, rows, chips, telemetry, `.settle`, `.scan`, `.pulse`) belongs to operation. The two must feel like one company, not one page. [HYPOTHESIS — the split; the brief asks for exactly this distinction]

## 6. Dashboard product philosophy

Derived from the briefs and the site's stated principles; each line is checkable against the code. [HYPOTHESIS as a whole]

1. **It is the console the site draws.** Same frames, same rows, same chips, same words, with the buttons active. A person who has seen dolmir.com recognises the product; a person who has not never sees marketing.
2. **A workspace, not a page.** A stable shell; panes that scroll inside themselves; the content area changes with the task; the page never scrolls sideways and rarely scrolls at all.
3. **Attention first, tables last.** The first screen answers "what needs a person now"; lists are views of work, not of tables; anomalies are signalled, reports are not produced.
4. **Every value carries its source.** A field is shown with where it came from (`source`), in the site's own idiom; the exact span or record is one click away; nothing is shown as verified that the platform did not verify.
5. **Uncertainty is amber, always and only.** FACT gets the green mark; everything the platform is not sure about is amber; NON DETERMINATO is a first-class state with "cosa mancherebbe", never an error.
6. **The yes is a person's, and it looks like one.** A proposed action is visibly proposed; an approval is a deliberate two-step act with a name and a time; "sent" appears only when the action record exists.
7. **DOLMIR speaks in the site's voice, as a colleague.** "Ha letto", "ha trovato", "propone", "non ha potuto determinare", "aspetta il tuo sì", "ha inviato". Never a model name, never a token count, never "l'AI".
8. **Nothing is invented for the screen.** No count without a query, no metric without a projection, no state the backend cannot report. When the backend cannot support an experience, the requirement is written down (§18), not simulated.

## 14. Approval experience

The site promises the moment: a person sees the request, the precedent and the difference, and says yes. The backend makes it a two-moment act. The UI must show every state the platform can be in, and no state it cannot. [HYPOTHESIS for the interaction; CONFIRMED for the states]

| State the platform reports                                                | Chip (site words)                              | Esito shows                                                                                                                           |
| ------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| recommendation `proposed`, level REQUIRE_APPROVAL, case awaiting_approval | **DECISIONE RICHIESTA** (amber, pulse)         | the reply, the decision card with APPROVA · RIFIUTA, "Niente parte da qui finché non hai detto sì"                                    |
| `proposed`, level DRAFT or SUGGEST                                        | "bozza" / "suggerimento" (neutral)             | the text DOLMIR wrote, marked "non inviabile da DOLMIR"; no approve control (the API refuses it); close manually                      |

Viewers see the card without controls and the line "Serve chi può approvare".

**What the site promises that the backend cannot do yet:** REVISIONA / MODIFICA — editing the draft and approving the edited text. ## 15. Evidence and trust experience

"DOLMIR knows this because…", in the site's idiom, with the platform's actual evidence kinds. [HYPOTHESIS for rendering; CONFIRMED for data]

- **On the surface:** every field carries a `source` line, in the site's own format: "email · «500 pezzi»" (DOCUMENT_SPAN), "allegato righe.csv · riga 3" (a child document), "anagrafica · email acquisti@officine-rossi.it" (RECORD_FIELD, alias kind), "regola · reply_language = it" (a rule). The state dot says how sure the platform is.
- **One click deeper — the inspector, "Cosa ha letto":** the source document rendered from `documents/:id/texts` with the cited span highlighted (offsets are exact); the message headers (from, subject, received); attachments with their text status ("PDF · non letto" for `unsupported`, honestly). For a RECORD_FIELD: the matched record and the alias that matched, with the resolver's reasons. For discarded readings: "DOLMIR aveva letto «…» ma non l'ha trovato nel messaggio: scartato."
- **Epistemic status → the site's grammar:** FACT → `verified` (VERIFICATO, green mark; only record fields, computations and citations qualify — the kernel enforces it); OBSERVATION → `read` (cyan dot: "letto nel messaggio"); NON_DETERMINATO → NON DETERMINATO (amber block, COSA MANCHEREBBE). **Gap:** the site has no word for ASSUMPTION (an interpretation layered on observations, e.g. a counterpart matched by name similarity) or HYPOTHESIS. Proposal, to be ratified by the website workstream: render both as the site's `unknown` state (amber italic) with the labels **DEDOTTO** and **IPOTESI**. An uncertain conclusion never wears the green mark. [HYPOTHESIS — new words]
- **Who decided, when, on what:** DECISIONE REGISTRATA · the approver (today "tu" or an anonymised id — §18) · time · note; the action's time and provider id; the case resolution.
- **What DOLMIR did not do:** a small block the positioning asked for ("a panel showing what the system did not do — the judgement calls it deliberately left to a person"): missing inputs left to a human, a refused draft, discarded readings, the price it will never propose. All from findings and `nonDeterminato`.
- **Technical toggle:** ids, hashes, versions, request ids, the policy version and the system version — present, collapsed, for support.

## 16. AI interaction model

Embedded, not conversational, for the whole of the first product. [HYPOTHESIS]

- **DOLMIR appears as a colleague's notes on the case, in the site's voice and tense:** "ha letto" (LEGGE), "ha trovato" / "ha verificato" (VERIFICA), "propone" (Esito), "si ferma: serve una persona" (SI FERMA), "non ha potuto determinare" (NON DETERMINATO), "aspetta il tuo sì" (APPROVAZIONE UMANA), "ha inviato" (AGISCE). Never "l'AI", never a model name, never a percentage.
- **The system's work is shown as state, not prose** (the console's principle: the two self-describing tools "are rendered as state instead of prose"). A case's stage strip and chips are the interface to the AI; there is no explanation paragraph generated for the screen.
- **No chat in Stages 3–6.** The agent conversation (M9) does not exist; when it does, its surface is the site's console, moved into the workspace: transcript + "Cosa sta facendo" + "DATI CONSULTATI" + the gate + NON DETERMINATO, using the same primitives. Until then the console stays on the public site as the demonstration it is.
- **Cost and models** stay in Impostazioni · Costi AI, for owners and admins, as an honest invoice line, never as a signal on a case.

## 19. What should NOT be built

### Technical architecture (unchanged from version 1, restated for completeness) [HYPOTHESIS — OD-15]

`apps/web` = Next.js 16 (App Router) + React 19 + Tailwind 4 + strict TypeScript, workspace package `@dolmir/web`, pinned to the site's versions (16.3.3 / 19.2.8 / 4.3.3). Type-only imports from `@dolmir/core` and `@dolmir/api` with a `Json<T>` mapped type (dates as strings), enforced by dependency-cruiser (`dependencyTypesNot: ['type-only']`). A `DataSource` interface with `ApiDataSource` and `FixtureDataSource`; server components for reads, server actions with an origin check for writes; a bounded re-fetch after an approval; no global client store; fonts self-hosted so builds need no network. A Vite single-page app was considered and rejected (token in the browser, CORS on the API, no server boundary).
